最近很火的鹈鹕测试，参考 [CodexRadar CUP](https://codexradar.com/cup/) 提供的 prompt：

```
创建一个HTML，内容是SVG绘制一个鹈鹕骑自行车的2D动画
```

我做了几轮测试。首先在自己现有 sys prompt 的基础上——就是 [CodeX system prompt 分享（2）](/posts/提示词分享_2/) 那份短合同——直接用 Astra Mid 和 Grok xhigh 做对比。

Grok 这一轮并不太理想：场景能看出来，但造型更像「椭圆拼出来的鸟 + 会转的轮子」，完成了 prompt 的字面要求，交付感偏薄。Astra 这边已经是一份带暂停、调速、腿部踩踏的完整小页面。

于是去看了 OpenAI 关于 skill 和 prompt 的思考：[Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)。群里很多兄弟也表示，适当改一下 system prompt 可能会有改善。大家提供的补丁是这段：

```markdown
## 质量与工作尺度
默认认真完成可交付结果，不因需求简短而降低质量。根据影响范围、失败后果、不确定性和验证难度确定工作深度，以相关证据和实际结果验证需求是否满足；
视觉任务应查看实际渲染，验证受阻时如实说明。进一步分析或检查应针对会影响实现或交付判断的具体问题；
验收要求满足、相关检查通过且无具体未解决问题时，及时交付，不因假设性风险重复推演或扩大范围。
```

补上之后，重启 Codex / Grok，重跑同一道鹈鹕题。

可以看得出来，Grok 有明显改善：海岸、木栈道、红车、喉囊里那条小鱼，都比第一轮更像一份能交出去的动画。Astra 的改善其实并不明显——第一轮就已经是完整页面，第二轮还是同一套气质，没有拉开差距。

这不是对照实验。同一条用户 prompt、同一份短 sys prompt，只改了有没有那段质量约束，每边各跑一轮，肉眼看交付。样本就这些。对我自己的用法，结论很具体：Grok xhigh 吃这段约束更明显；Astra Mid 对「需求很短也要认真做完」本来就不那么依赖。
